## Summary

> One paragraph: what does this RFC propose, and what problem does it solve? A reader should be able to answer "should I keep reading?" from this section alone.

## Motivation

> Why does this need to change now? Cite the concrete pain or risk being addressed. Reference prior discussion, related RFCs, or external context where relevant.

## Scope

> What is in scope, and explicitly what is out of scope. Use this section to prevent scope creep during review.

## Specification

> The normative content of the RFC. Use MUST / SHOULD / MAY per RFC 2119 where applicable. Schemas, field tables, and tool signatures live here. For protocol-changing RFCs this is typically the longest section.

## Canonical events / Protocol changes

> _Optional for non-protocol RFCs._ Enumerate the canonical events (state transitions, lifecycle changes, message types) introduced, modified, or deprecated by this RFC. Include exact field changes against existing schemas.

## Backward compatibility

> Explicitly state whether this RFC is additive, soft-deprecating, or breaking. Describe the migration path. Reference RFC-001 §3.6 (deprecation policy) and §3.7 (version coexistence) where applicable.

## Security, privacy, and compliance considerations

> Threat model deltas, PII exposure changes, regulatory implications. RFCs touching `restricted` data per RFC-004 §3.3 MUST explicitly address access, retention, and audit.

## Reference implementation impact

> What changes does this require in any reference implementation? Keep this neutral — describe the surface area, not specific implementer roadmaps. RFC acceptance is independent from implementation adoption.

## Alternatives considered

> List the alternatives evaluated and explain why they were rejected. A reader should be able to verify that the chosen path is not the only one that was considered.

## Open questions

> Unresolved questions that the comment window should help close. Number them so reviewers can reference specific items.

## Decision

> Populated by the maintainer at acceptance. Records: decision (Accepted / Rejected / Withdrawn), date, rationale summary, and references to any formal objections (per RFC-001 §3.10) and their resolution. If an RFC is returned to Draft, that is recorded as a transition note inside the RFC itself, not as a terminal decision. Empty while the RFC is in Draft, Open for Comment, or Final Comment Period.
