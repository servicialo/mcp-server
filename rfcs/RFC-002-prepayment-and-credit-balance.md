> **ES:** Define el modelo formal de prepago en Servicialo: **Credit Balance del cliente** — saldo monetario que se consume al ejecutar Services, agnóstico al Service Order. Append-only, composable con suscripciones, packs y memberships. Cierra la ambigüedad entre §12.8 (prepayment REST flow ya existente) y los estados financieros del Service atómico.
>
> **EN:** Defines the formal prepayment model in Servicialo: **client-level Credit Balance** — a monetary balance consumed as Services are delivered, agnostic to any Service Order. Append-only, composable with subscriptions, packs and memberships. Closes the ambiguity between §12.8 (existing prepayment REST flow) and the financial states of the atomic Service.

---

## 1. Summary / Resumen

**ES:** Introducir un objeto de primera clase `CreditBalance` que representa un saldo monetario que un cliente mantiene con una organización, modelado como un registro append-only de entradas (credit / debit). Las entradas se generan por: pago anticipado, refund (RFC-003), consumo automático cuando se cobra un Service, o ajuste manual. El balance computado es `sum(credit) − sum(debit)`, MUST ser ≥ 0. Cuando un Service prepagado se `documented`, el sistema MUST consumir del balance automáticamente y la transición `collected` se aplica con `payment_source: "credit_balance"` en metadata.

**EN:** Introduce a first-class `CreditBalance` object representing a monetary balance a client holds with an organization, modeled as an append-only log of entries (credit / debit). Entries are generated by: prepayment, refund (RFC-003), automatic consumption when a Service is charged, or manual adjustment. The computed balance is `sum(credit) − sum(debit)`, MUST be ≥ 0. When a prepaid Service transitions to `documented`, the system MUST automatically consume from the balance and the `collected` transition is applied with `payment_source: "credit_balance"` in metadata.

---

## 2. Motivation / Motivación

**ES:** v0.9 ya soporta prepayment como REST flow (§12.8 — POST /checkout → paymentIntentId → scheduling.book). Lo que falta es:

1. **El mapping del prepaid al ciclo de vida atómico.** Una sesión `requested` con `billing.status = paid` viola la regla de §6.5 (payroll = solo `collected`). El provider está prestando un servicio cuyo dinero ya entró, pero el lifecycle dice que el dinero entra recién en estado 8.
2. **El modelo para suscripciones, packs, memberships.** Hoy no hay forma de modelar "el cliente compró un pack de 10 sesiones por $500". Hay que crear 10 Services o forzar el modelo a un Service Order — ninguno es natural.
3. **Composabilidad con refunds.** Si una sesión prepagada se refunda, ¿devolvés al cliente vía external payment o le acreditás contra futuras sesiones? Sin Credit Balance no hay segunda opción.
4. **Trazabilidad cross-Order.** Un cliente que compró un pack y después contrató un Service Order debe poder usar el saldo del pack contra el Order. Sin un objeto Credit Balance, esto se modela como hack ad-hoc en cada implementación.

**EN:** v0.9 already supports prepayment as a REST flow (§12.8 — POST /checkout → paymentIntentId → scheduling.book). Missing:

1. **Mapping from prepaid to atomic lifecycle.** A `requested` session with `billing.status = paid` violates the §6.5 rule (payroll = `collected` only). The provider is delivering a service whose money already arrived, but the lifecycle says money arrives only at state 8.
2. **Model for subscriptions, packs, memberships.** Today there is no way to model "the client bought a 10-session pack for $500". Either 10 Services upfront or shoehorn into a Service Order — neither is natural.
3. **Composability with refunds.** When a prepaid session is refunded, do you refund externally or credit toward future sessions? Without Credit Balance, only option one exists.
4. **Cross-Order traceability.** A client who bought a pack and later signed a Service Order should be able to use the pack balance against the Order. Without a Credit Balance object, every implementation hacks this differently.

## 3. Detailed Design / Diseño Detallado

### 3.1 Conceptual model / Modelo conceptual

```
Client
  │
  ├── CreditBalance (per organization, per currency)
  │     │
  │     ├── balance: amount (computed)
  │     │
  │     └── entries[] (append-only)
  │           ├── credit entries: prepayment, refund, adjustment+
  │           └── debit entries: consumption, adjustment-
  │
  ├── Service A ──► billing.status: paid (settled by credit balance)
  ├── Service B ──► billing.status: paid (settled by credit balance)
  └── Service C ──► billing.status: pending (no balance available)
```

**Invariants / Invariantes:**

- `balance = Σ(credit.amount) − Σ(debit.amount)`
- `balance ≥ 0` at all times (no overdrafts in v1.0)
- Entries are append-only — never edited or deleted
- Each entry has a stable, idempotent `id`
- Each entry has exactly one `source` (typed)

### 3.2 CreditBalance object / Objeto CreditBalance

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `client_id` | string | REQUIRED | Beneficiary / client identity |
| `organization_id` | string | REQUIRED | Organization holding the balance |
| `currency` | string (ISO 4217) | REQUIRED | Balance currency. A client MAY have multiple balances (one per currency). |
| `balance` | number | REQUIRED | Computed: sum of credits minus sum of debits |
| `entries_count` | integer | OPTIONAL | Total entries for quick pagination |
| `last_entry_at` | datetime | OPTIONAL | Timestamp of most recent entry |
| `created_at` | datetime | REQUIRED | When the balance object was created (first entry) |
| `metadata` | object | OPTIONAL | Implementation-specific data. Protocol does not interpret. |

### 3.3 CreditBalanceEntry object / Objeto CreditBalanceEntry

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `id` | string (UUID v4) | REQUIRED | Unique entry identifier |
| `client_id` | string | REQUIRED | Parent client |
| `organization_id` | string | REQUIRED | Parent organization |
| `currency` | string (ISO 4217) | REQUIRED | Entry currency. MUST match parent balance currency. |
| `type` | enum | REQUIRED | `credit` (increases balance) or `debit` (decreases balance) |
| `amount` | number | REQUIRED | Always positive — `type` determines direction. MUST be > 0. |
| `source` | enum | REQUIRED | `prepayment` \| `refund` \| `consumption` \| `adjustment` (see §3.4) |
| `reference_id` | string | CONDITIONAL | Required for `consumption` (sale_id) and `refund` (credit_note_id). |
| `payment_id` | string | OPTIONAL | External payment reference for `prepayment` source |
| `occurred_at` | datetime | REQUIRED | When the entry was recorded. ISO 8601. |
| `idempotency_key` | string | OPTIONAL | If present, server MUST treat duplicate keys as the same entry |
| `description` | string | OPTIONAL | Human-readable label |
| `metadata` | object | OPTIONAL | Implementation-specific |

### 3.4 Entry sources / Fuentes de entrada

| Source | Type | When generated |
|--------|------|----------------|
| `prepayment` | credit | Client pays before any specific Service is identified (pack, subscription, deposit) |
| `consumption` | debit | A Service moves to `documented` and is automatically settled by the balance |
| `refund` | credit | A credit note (RFC-003) is issued and the refund is delivered as balance credit |
| `adjustment` | credit or debit | Manual adjustment by org admin (audit-logged, requires `mandate:admin` scope) |

Implementations MAY define additional sources prefixed with `x-` (e.g., `x-promotion`).

### 3.5 Interaction with the atomic Service lifecycle / Interacción con el ciclo de vida

The 6+3 universal states (§6 of PROTOCOL.md) remain unchanged. **No new state is introduced.** The interaction is via the `billing.status` track and the `lifecycle.transitions` metadata.

**Pre-paid session flow:**

```
requested  → billing.status = pending, no credit consumed
scheduled  → billing.status = pending
confirmed  → billing.status = pending
in_progress → billing.status = pending
completed  → billing.status = pending
documented → ★ AUTOMATIC: payments.consume_credit (server-side)
                          - check client balance ≥ service amount in service currency
                          - if yes: emit debit entry of type=consumption
                          - emit lifecycle transition: documented → collected
                                with metadata: { "payment_source": "credit_balance", "entry_id": "..." }
                          - billing.status = paid
                          - service.invoiced and service.collected timestamps recorded
                          - if NO: billing.status stays pending → flow continues via post-service settlement (§12.8.2)
verified   → on client confirmation or auto-verify
```

**Post-service settlement flow (unchanged from v0.9):** No credit balance involved; payments.create_sale + payments.record_payment work as today.

### 3.6 Effect on payroll rule (§6.5) / Efecto en la regla de payroll

The §6.5 rule "implementations that calculate provider compensation MUST read only sessions in `collected` state" is **preserved**. The Credit Balance model satisfies it because:

- A prepaid session moves through `documented → collected` automatically when balance is sufficient.
- The `collected` transition records `payment_source: "credit_balance"` so payroll calculators can audit how settlement happened.
- A session whose balance is insufficient does NOT transition to `collected` automatically — it follows post-service settlement. Provider compensation only applies once `collected` is reached, which is the existing rule.

### 3.7 Multi-currency handling / Manejo multi-currency

A single client MAY hold multiple Credit Balances, one per currency. Example:

```
client_123 + org_abc + currency: USD → balance $200
client_123 + org_abc + currency: MXN → balance $0
client_123 + org_xyz + currency: USD → balance $50
```

A Service in MXN consumes only the MXN balance. There is **no automatic FX conversion** in v1.0. Cross-currency conversion is reserved for v1.1 (RFC TBD, Gap 2 / multi-currency + tax).

### 3.8 Tools / Herramientas

#### 3.8.1 New tools (additive)

| Tool | Description | Required scopes |
|------|-------------|------------------|
| `payments.get_credit_balance` | Get balance for `(client_id, organization_id, currency)`. Returns balance + recent entries. | `payment:read` |
| `payments.list_credit_balance_entries` | List entries with pagination + filters (`source`, `date_range`). | `payment:read` |
| `payments.record_prepayment` | Record a prepayment as a credit entry. Inputs: `client_id`, `amount`, `currency`, `payment_id` (external ref), optional `description`, `metadata`. | `payment:write` |
| `payments.adjust_credit_balance` | Manual adjustment. Inputs: `client_id`, `amount`, `currency`, `direction` (credit/debit), reason. Requires `mandate:admin`. | `mandate:admin` + `payment:write` |

#### 3.8.2 Modified tools

| Tool | Change | Backward compatibility |
|------|--------|------------------------|
| `payments.record_payment` | Unchanged semantically — still ties to a `sale_id`. No signature change. | Full backward compat. |
| `payments.create_sale` | When a balance exists in the service currency for the client, MUST attempt credit consumption before requiring external payment. Behavior change is server-side only — tool signature unchanged. | Full backward compat from API perspective; behavior changes for clients with balances (this is the intended improvement). |
| `payments.get_status` | Output extended: response MAY include `credit_balance_consumed` field when settlement involved the balance. | Additive only. |

#### 3.8.3 New scopes

This RFC does NOT introduce new scopes — `payment:read`, `payment:write`, and `mandate:admin` cover the new tools.

### 3.9 Manifest declaration / Declaración en el manifest

Implementations that support Credit Balance MUST declare it in `registry.manifest`:

```json
{
  "capabilities": {
    "credit_balance": {
      "supported": true,
      "currencies": ["USD", "MXN", "CLP"],
      "max_balance_per_client": null
    }
  }
}
```

Implementations that do NOT support Credit Balance return `supported: false` and reject all four new tools with `HTTP 501 Not Implemented` (REST) or MCP error `tool_not_supported`.

### 3.10 JSON Schema / Schema JSON

A new file `schema/credit-balance.schema.json` defines both `CreditBalance` and `CreditBalanceEntry`. The file references `schema/service.schema.json` for the implicit consumption relationship but does not modify it.

### 3.11 Audit and idempotency / Auditoría e idempotencia

- Every entry creation MUST produce an audit entry per §10.6.
- `payments.record_prepayment` and `payments.adjust_credit_balance` MUST accept an idempotency key. If absent, the server SHOULD derive one from request fingerprinting.
- Duplicate idempotency keys MUST return the existing entry (HTTP 200 with `idempotent: true` marker), not create a new one.

### 3.12 Edge cases / Casos límite

| Case | Behavior |
|------|----------|
| Service amount > balance, service in same currency | No automatic consumption. Service stays in post-service settlement track. Implementation MAY suggest topping up the balance. |
| Service amount > balance, partial consumption supported (impl flag) | Implementation MAY partially consume balance and require the remainder externally. Off by default — requires explicit manifest capability declaration `partial_consumption: true`. |
| Service in currency client has no balance for | Falls through to post-service settlement. |
| Balance refunded externally (cash payout) | Emit a debit entry with `source: adjustment` and `description: "external refund"`. The audit trail preserves the external nature. |
| Service is cancelled after prepayment | Refund flow (RFC-003) determines whether to issue an external refund or add a credit entry. Default: credit back to balance, audit-logged. |

## 4. Drawbacks / Inconvenientes

**ES:**
- **More complexity for solo practitioners.** A freelancer doing 1:1 invoicing does not need this. The model is OPTIONAL and gated behind a manifest flag, but reading the spec for the first time, the section is larger than a v0.9 reader expects.
- **Storage growth.** Append-only ledgers grow indefinitely. Implementations must plan archive/snapshot strategies for high-volume clients (e.g., a corporate client running thousands of services per month).
- **Idempotency complexity.** Every implementation needs robust idempotency on credit entries. Getting this wrong silently double-counts money.
- **No automatic FX conversion in v1.0.** A client paying in USD whose Service is priced in MXN must either: (a) the org accepts the USD balance against the MXN service via implementation policy, or (b) the client tops up in MXN. v1.0 punts on cross-currency.

**EN:** Same as above.

## 5. Alternatives Considered / Alternativas consideradas

### 5.1 Escrow per Service Order (rejected)

Tie prepaid funds to a specific Service Order instead of the client. Money sits in escrow per Order, gets released as Services are verified.

**Rejected because:** breaks the most common case — packs and subscriptions are not Service Orders, they're light-weight credit-and-consume. Forcing an Order wrapper for "client bought 10 sessions" creates ceremony with no benefit. The Escrow model also makes cross-Order credit reuse impossible (a client switching from a pack to an Order loses the leftover balance).

### 5.2 Per-Service prepaid flag (rejected)

Add `billing.prepaid: true` boolean to each Service, with `billing.payment_id` linking the prepayment.

**Rejected because:** does not address subscriptions, packs, or multi-Service prepayments. Treats prepayment as a single-Service property when in reality it is a client-level relationship.

### 5.3 New lifecycle state `prepaid` (rejected)

Add `prepaid` as a new state between `requested` and `scheduled`.

**Rejected because:** breaking change to the 9 universal states. Violates Principle 6 (delivery is separate from agreement / payment). The lifecycle should not track payment flow — that is what `billing.status` is for.

### 5.4 External wallet / payment service abstraction (rejected for v1.0)

Treat balances as living in an external service (Stripe Customer Balance, Mercado Pago wallet, etc.) and have the protocol query the external service.

**Rejected because:** requires every implementation to integrate with a specific payment provider. The protocol stays implementation-agnostic. Implementations MAY back the Credit Balance with Stripe Customer Balance internally, but the protocol surface remains uniform.

## 6. Unresolved Questions / Preguntas abiertas

1. **Should negative balances be permitted (credit line / "fiar")?** Current proposal: NO for v1.0 (`balance ≥ 0` invariant). Future RFC may allow opt-in credit line with explicit terms. Some verticals (clinics fiando a pacientes) want this.

2. **Should balance expiration be a protocol concern?** Current proposal: NO — implementations MAY apply expiration as an internal policy but the protocol does not model `expires_at` on entries. Risk: customer disputes about expired credit; mitigated by per-impl T&C.

3. **Transferability between clients?** E.g., a parent paying a child's balance. Current proposal: NO direct transfer — use `payer_id` separation (already in §5.3). Future RFC if demand emerges.

4. **Snapshot / archival API?** For high-volume clients, queries over the full entry history become slow. Should the protocol prescribe a snapshot tool? Current proposal: NO — implementations decide. Add tool later if cross-impl benchmark queries require it.

5. **Insurance reimbursement modeling.** An insurer paying after the service is similar but flows in the opposite direction (charged before paid). Currently modeled implicitly via `billing.status = charged` (§12.8.1). Should this also use the credit balance pattern? Current proposal: NO — insurance flow has different audit requirements (claims, denials, partial payments). Reserved for a separate v1.x RFC.

6. **Refund of unconsumed credit balance.** When a client wants their prepaid funds back as cash (not future-credit), the current model has no dedicated tool. Workaround: emit a credit note (RFC-003) with `settlement.method = external_refund` against an artificial "deposit sale" — but credit balance entries are intentionally agnostic to sales, so the workaround is awkward. Should v1.0 add a `payments.refund_credit_balance` tool, or wait for v1.x evidence of demand? Use cases: gym membership cancellations, legal retainer terminations, refund-on-death policies.

7. **Hour-denominated rollover.** Legal retainers and many professional service packages express in hours, not money (e.g., "$1,000/month = 10 hours @ $100"). The current model is money-only. Should v1.0 add an optional `units` field alongside `amount` (with conversion rules), or leave hour-tracking to implementations? Current recommendation: leave money-only for v1.0 (adds significant complexity, money covers most cases); revisit if multiple implementers request units-based balances.

8. **Transferability across Service Orders for the same client.** The model is intentionally Order-agnostic — credits live at the (client, organization, currency) tuple, so a client can use leftover pack credit against a later Service Order without any explicit transfer step. This is **implicit** behavior in v1.0; should it be made explicit in spec text to avoid implementer confusion? Current recommendation: yes, add a clarifying paragraph in §3.7 (Multi-currency handling) extending it to also clarify Order-independence.

## 7. Migration Path / Camino de Migración

### 7.1 Backward compatibility / Compatibilidad hacia atrás

- All v0.9 tools retain their signatures unchanged.
- `payments.create_sale` adds server-side balance check before falling through to current post-service settlement. Clients that never call `payments.record_prepayment` see exactly v0.9 behavior.
- `registry.manifest` declares Credit Balance support as a capability. v0.9 clients ignore unknown fields per §15.5.

### 7.2 New required behavior / Comportamiento nuevo requerido

For implementations claiming v1.0 conformance:

- MUST implement `payments.get_credit_balance` returning balance = 0 (and accepting writes) if the org currently has no credit balance for the client. NOT supporting it returns `HTTP 501` per §3.9.
- MUST honor idempotency keys on `payments.record_prepayment`.
- MUST emit audit entries per §10.6.

Implementations claiming v1.0 conformance MAY choose to **not** implement Credit Balance — they must declare `credit_balance.supported: false` in the manifest. This is an OPTIONAL capability.

### 7.3 Deprecations / Deprecations

This RFC introduces **no deprecations**.

### 7.4 Implementation downstream

Reference implementations adopting this RFC manage their own downstream roadmaps (database schema, business logic, UI, tests). Servicialo SpA does not prescribe or coordinate implementer roadmaps; the protocol surface defined in this RFC is what conformance is measured against.
