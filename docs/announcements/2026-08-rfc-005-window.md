## The window

| | |
|---|---|
| **RFC** | [RFC-005: Period Deliveries](https://github.com/servicialo/mcp-server/pull/21) |
| **Category** | Minor — a new OPTIONAL field with a default, additive |
| **Window opened** | 2026-08-23 |
| **Comment period** | through **2026-09-06** |
| **Final comment period** | **2026-09-06 → 2026-09-13** |
| **Venue** | PR #21 |

It adds `kind: occurrence | period` to the Delivery, with a mandatory `{start, end}`
window for `period`, so that an availability obligation satisfied across a window is a
delivery rather than an absence. The case that forces it: a monthly retainer billed in
a month with zero consumed hours. Without it, an implementation either invents a
zero-duration phantom delivery or emits a settlement with no delivery at all — two
conforming implementations, two incompatible models.

## How it got here

Every step below is on the record and linked, because a process that cannot be
audited is a claim, not a process.

**2026-08-23 — a case stress test.** Nine cases drawn from real professional-services
arrangements — retainers, milestone B2B repair, mixed-payer cohorts, delegated agents,
partial delivery with chargeback, agent-to-agent translation under SLA, and a
chain-subcontracting anti-pattern — produced twelve questions. Each was checked
against the specification *before* becoming anything: two were dropped because the
spec already answered them, and three were narrowed. A question the spec already
answers does not become an issue; publishing one damages the public signal.

**The cohort, same day.** [RFC-005](https://github.com/servicialo/mcp-server/pull/21)
(period deliveries), [Proof of Service 0.3.0](https://github.com/servicialo/mcp-server/pull/22)
(the proof consumer / relying party), the
[vocabulary migration plan](https://github.com/servicialo/mcp-server/pull/23), and ten
issues ([#25](https://github.com/servicialo/mcp-server/issues/25)–[#34](https://github.com/servicialo/mcp-server/issues/34))
covering order amendment, settlement holdback, pricing units, shared evidence
artifacts, acceptance authority, consumer conformance, settlement allocation,
chargebacks, version negotiation, and documentation fixes.

**An independent blind review.** The six design decisions the cohort embodies were put
to a second AI system **without access to any of the published decisions**. It was
given the primitives and the case, and asked to decide. It
[converged on five of six](https://github.com/servicialo/mcp-server/pull/21#issuecomment-5388096195),
including RFC-005's central choice, which it reached for a reason the RFC states
independently: under the alternative, *"the money exists, but the object against which
to prove fulfilment does not."* Its three additional proposals are on the PR as input
to this window.

**Then a source audit.** The same reviewer ran a second and different pass:
verification against the raw files, with a URL cited per claim. Eight claims from the
cohort were checked — **seven verified, one refuted** — and anything that could not be
read cleanly was returned as *not verified* rather than guessed, which is what makes
the other seven worth anything.

The refuted one was a table row in
[#32](https://github.com/servicialo/mcp-server/issues/32) that called RFC-003's
`reason_code` enum closed and concluded no value applied. It was wrong twice: the row
listed `other`, defined as *"implementation-defined"*, and §3.3 explicitly permits
`x-` prefixed codes. The
[correction](https://github.com/servicialo/mcp-server/issues/32#issuecomment-5388255287)
was published the same day as a dated amendment rather than a silent edit — under a
day in public. The issue's conclusion did not change; its evidence did, from *no value
exists* to *a value exists and it is the wrong object*.

The audit's own contribution — [four anti-abuse rules](https://github.com/servicialo/mcp-server/pull/21#issuecomment-5388268327)
for `kind: period`, each requiring a negative conformance fixture — is also on the PR.

The blind phase and the audit phase are reported separately on purpose: the first
converged without seeing the answer, the second was written having read the draft.
Only the first is evidence of independent convergence, and conflating them would
overstate it.

## Three doors

Pick by what you build. None of them requires the other two.

| If you build | Start at | Why this one |
|---|---|---|
| **A platform** that schedules, verifies or settles professional services | [RFC-005 (#21)](https://github.com/servicialo/mcp-server/pull/21) | Retainers, stand-by agreements and maintenance contracts are a large share of professional services. If you bill any of them, this decides whether your charges have anything to point at. The window is open now. |
| **An agent** that calls Servicialo | [#30 — consumer conformance profile](https://github.com/servicialo/mcp-server/issues/30) | Every existing conformance level asks you to build a backend. This one asks a caller to respect mandate scopes and degrade gracefully when a mandate is revoked — a conformance claim reachable in an afternoon. The requirement already exists in `§10.5`/`§10.7`; the profile that would let you declare it does not. |
| **A contribution**, and you want a well-bounded first one | [#33 — version negotiation (`help wanted`)](https://github.com/servicialo/mcp-server/issues/33) | The design is already decided by RFC-001. The acceptance criteria are mechanical and testable, it touches none of the protocol's contested ontology, and two v1.0 changes are blocked behind it. One judgement call, with three written-out options. |

## Where the network actually stands

One implementation in production — the reference one. **Zero independent
implementations verified.** Live counts are at
[servicialo.com/network](https://servicialo.com/network); verified implementations, when
there are any, are listed at
[servicialo.com/implementors](https://servicialo.com/implementors).

That is the honest position, and the comment windows exist to change it. A protocol
with one implementation is a design; the second implementation is what makes it a
standard, and the questions worth answering before 1.0 are the ones a second
implementer would hit first. That is what this cohort is trying to find out while
changing the answer is still cheap.

If you run a node, `SERVICIALO_IMPL_NAME`, `SERVICIALO_IMPL_URL` and
`SERVICIALO_IMPL_CONTACT` identify it — see
[Identify your node](https://github.com/servicialo/mcp-server/blob/main/packages/mcp-server/README.en.md#identify-your-node)
for exactly what leaves your machine under each one. It is opt-in, and an anonymous
node is fully conformant.

## Process caveat, stated rather than discovered

RFC-001 — the document defining this process — is itself an open RFC on an unmerged
PR, in `Draft — Open for Comment` since 2026-05-18. The process RFC-005 is following
has not been ratified. That is the position of a protocol bootstrapping its own
governance, and it is better said than found.
